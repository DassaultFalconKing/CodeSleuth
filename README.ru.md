```text

```

**Дисциплина работы LLM с репозиториями кода.**

CodeSleuth — небольшой слой дисциплины для агентов программирования. Он объединяет переиспользуемые Skills для ревью, профили репозиториев, устойчивые соглашения по доказательствам, терминальную панель управления и несколько ограниченных инструментов для работы с репозиторием. Хост-агент по-прежнему владеет моделью, контроллером, сессией, разрешениями, маршрутизацией инструментов и циклом выполнения.

Текущая версия: **0.4.0**.

Текущая базовая реализация:

- **Update** для исходного checkout явно получает актуальный `origin/main` и выполняет только fast-forward чистого локального `main`, игнорируя устаревшие метаданные отслеживания ветки;
- активная поверхность TUI остаётся в верхней части области содержимого; большой блок бренда и нижний Footer можно скрывать независимо друг от друга;
- левую навигацию можно сворачивать/восстанавливать, а правую панель Keys/Help — сворачивать/восстанавливать или закрывать на текущую TUI-сессию;
- внешний MCP-адаптер доказательств привязан к репозиторию, ограничен и усилен как поверхность доказательств только для чтения, а не как альтернативная среда выполнения агента.

| Поверхность | Статус |
| --- | --- |
| OpenCode | текущая полная установленная интеграция хоста |
| NovaClaw | текущий внешний хост через MCP-доказательства только для чтения |
| Codex, Cursor, Hermes, BodegaOne, Pi-harness | запланированные цели интеграции хостов после усиления |
| Среда выполнения модели / supervisor, принадлежащие CodeSleuth | намеренно не являются частью продукта |

# Основы

## Какую проблему решает CodeSleuth?

LLM хорошо читают код, но работа с большими репозиториями проваливается очень предсказуемыми способами:

- репозиторий больше полезного рабочего контекста модели;
- найти файлы — не то же самое, что понять их;
- сводка scout-агента или субагента может быть ошибочной;
- длинное ревью может потерять состояние после compaction или в новой сессии;
- PR может выглядеть корректно локально, одновременно ломая неизменённого вызывающего потребителя, схему, миграцию, тест или эксплуатационный контракт;
- агенты часто заявляют больше покрытия, чем реально выполнили.

CodeSleuth даёт хост-агенту повторяемую дисциплину для этих проблем:

```text
репозиторий
  -> детерминированная инвентаризация
  -> ограниченная проверка
  -> карта архитектуры/контекста
  -> точные доказательства из исходников
  -> верификация
  -> находка/отчёт/контрольная точка
```

Простое правило: **обнаруживай широко, проверяй узко и сохраняй то, что важно.**

## Что он умеет сегодня?

CodeSleuth поддерживает:

- ревью всего репозитория;
- ревью больших PR или диапазонов коммитов;
- построение карт архитектуры и компонентов;
- документацию репозитория, выведенную из текущего кода/конфигурации/тестов;
- ревью контрактов кода и API/схем;
- проверку согласованности тестов/CI/документации;
- проходы по безопасности, авторизации, области действия, состоянию, восстановлению, конкурентности, персистентности и миграциям;
- ревью с ограничениями ресурсов и больших входных данных;
- возобновляемые ревью с устойчивыми находками и контрольными точками;
- профили репозиториев для фокуса и рекомендаций по верификации, специфичных для языка/фреймворка;
- локальные аналитические отчёты, пригодные для повторного использования последующими сессиями в том же worktree;
- ограниченные проекции контекста с необязательным рендерингом Mermaid;
- доказательства репозитория только для чтения для внешних MCP-хостов;
- обратимые install/update/uninstall и необязательную фиксацию зависимости на точной версии.

Он делает это **не заменяя модели, агентов, инструменты и команды OpenCode** или эквивалентные средства среды выполнения другого хоста.

## Чего он не делает?

CodeSleuth — это не:

- среда выполнения модели;
- универсальный supervisor агентов;
- второй маршрутизатор инструментов;
- независимый заменяющий движок ревью;
- магический оракул покрытия;
- причина доверять сгенерированной диаграмме или сводке scout-агента как доказательству;
- пока ещё не менеджер пакетов для произвольных расширений.

Ядро намеренно мало. Рост должен происходить в Skills, профилях, Playbooks, инструментах, плагинах и адаптерах хостов.

## Текущая модель выполнения

Для установленной интеграции OpenCode:

```text
CodeSleuth -> конфигурация / Skills / профили / дисциплина доказательств / TUI
OpenCode   -> модель / контроллер / агенты / инструменты / выполнение
```

Для внешнего хоста:

```text
CodeSleuth -> поддерживаемые Skills и/или узкие интерфейсы доказательств
Хост       -> модель / контроллер / разрешения / инструменты / выполнение
```

Хост всегда остаётся источником полномочий на выполнение.

# Руководство пользователя

## Быстрый старт

### Требования

Для текущей полной интеграции OpenCode:

- Git **2.35+**;
- Python **3.10+**;
- OpenCode, доступный как `opencode`;
- необязательно Bun для запуска development-gates состояния/графа контекста на TypeScript.

TUI использует изолированную среду выполнения, которая устанавливает Textual из `pack/.opencode/bin/requirements-tui.txt` (`textual>=8.2.8,<9`), если текущий интерпретатор ещё не предоставляет совместимую версию Textual 8.x.

### Запуск TUI из checkout CodeSleuth

Linux/macOS/WSL:

```bash
./codesleuth /path/to/project
```

PowerShell:

```powershell
.\codesleuth.ps1 C:\path\to\project
```

Допускается вложенный путь; CodeSleuth нормализует его до корня содержащего Git-репозитория.

### Первый запуск

1. Откройте **Configure**.
2. Выберите поведение install/update/adopt.
3. Оставьте автоматическое определение профиля репозитория, если только репозиторий не является необычным или смешанным.
4. Выберите preset разрешений. `review-safe` — значение по умолчанию с минимальными привилегиями.
5. При необходимости выберите Agent profile/model для интеграции OpenCode.
6. Примените конфигурацию.
7. Запустите **Verify**.
8. Выберите **Open CodeSleuth**, чтобы запустить настроенную среду OpenCode.
9. В OpenCode начните с `/repo-prompts` для совета по задаче или с `/repo-review` для полного evidence-first ревью.

Для прямой неинтерактивной установки:

```bash
./install.sh /path/to/project
```

PowerShell:

```powershell
.\install.ps1 C:\path\to\project
```

Для проекта, который должен записывать точную ревизию исходников CodeSleuth как Git-зависимость:

```bash
./install.sh /path/to/project --bind-dependency
```

Это добавляет в staging `.gitmodules` и gitlink `tools/codesleuth`. CodeSleuth **не** выполняет commit или push целевого репозитория.

## Подробно

### Важные термины

| Термин | Значение |
| --- | --- |
| **Host** | Реальная среда coding-agent. Она владеет сессией модели, контроллером, маршрутизацией инструментов и выполнением. OpenCode — текущий полный хост; NovaClaw — первый внешний MCP-хост. |
| **Skill** | Переиспользуемый пакет протокола/инструкций, определяющий, как хост должен выполнять некоторый класс работы. |
| **Command** | Пользовательская команда хоста, направляющая работу в Skill или workflow. В OpenCode это команды `/repo-*`. |
| **Playbook** | Готовый к запуску рецепт задачи, сгенерированный для конкретного репозитория/задачи. Это рецепт prompt, а не Skill. |
| **Profile** | Метаданные типа репозитория: доказательства определения, фокус ревью, значения конфигурации по умолчанию и рекомендуемая верификация. Профили не выдают разрешения. |
| **Agent profile** | Специфичный для OpenCode выбор семейства моделей (`native`, `open-weight`, `codex`, `claude`). Он не устанавливает supervisor prompt CodeSleuth. |
| **Tool** | Небольшая исполняемая возможность, например детерминированная инвентаризация, устойчивое состояние ревью или операции графа контекста. |
| **Plugin** | Нативная интеграция хоста, загружаемая хостом, например поддержка review-compaction. |
| **Review state** | Локальное структурированное состояние продолжения в `.opencode/state/`, используемое для безопасного возобновления после compaction/прерывания сессии. |
| **Report** | Читаемый человеком/ассистентом Markdown в `.codesleuth/reports/`. Отчёты суммируют работу; они не являются runtime-состоянием. |
| **Context graph** | Ограниченная производная проекция репозитория для навигации/контекста. Она перестраиваема и никогда не является более сильным доказательством, чем исходный код. |

### Встроенные Skills

Текущие распространяемые Skills находятся в `pack/.opencode/skills/`:

- **`repository-deep-review`** — картирование больших репозиториев, документация, ревью всего репозитория и больших PR с устойчивыми контрольными точками;
- **`codesleuth-reports`** — записывает и поддерживает аналитические отчёты в `.codesleuth/reports/`;
- **`feature-porting-discipline`** — evidence-first перенос возможностей между репозиториями без копирования архитектуры, специфичной для исходника, и без создания дублирующей runtime-власти.

У протокола deep-review есть несколько правил, не подлежащих обсуждению:

1. контекст — это рабочая память, а не репозиторий;
2. inventory/discovery — не семантическое покрытие;
3. сводки scout-агентов — зацепки, а не находки;
4. существенные находки требуют точных доказательств из текущих исходников;
5. продолжением владеет устойчивое состояние, а не история чата;
6. тест/проверка считается пройденным только если он действительно успешно выполнялся;
7. агент проверяет реально запрошенный HEAD/range/worktree, а не устаревшую сводку.

### Встроенные профили репозиториев

Текущие встроенные профили:

```text
generic
rust
python
node
typescript
```

Автоматическое определение профиля использует **отслеживаемые Git-файлы**, а не произвольное содержимое файловой системы. Примеры:

- `Cargo.toml` / отслеживаемые `.rs` -> Rust;
- `pyproject.toml`, `requirements.txt`, `setup.py` или отслеживаемые `.py` -> Python;
- `package.json` -> Node;
- `tsconfig*.json`, отслеживаемые `.ts` / `.tsx` -> TypeScript.

Профили могут добавлять фокус ревью и рекомендации по верификации. Они **не** расширяют молча разрешения на web, edit, shell или внешние каталоги.

### Preset-ы разрешений

TUI предоставляет три preset-а:

| Preset | Назначение |
| --- | --- |
| `review-safe` | минимальные привилегии; безопасная Git-инспекция разрешена, а широкие shell/edit/web-действия остаются контролируемыми |
| `balanced` | дополнительно разрешает обычные команды верификации проекта, такие как pytest, cargo tests/checks и команды lint/typecheck/test менеджеров пакетов |
| `autonomous` | широко разрешает shell-работу, при этом продолжает спрашивать перед разрушительными/публикующими Git-действиями, такими как push/reset/clean |

Явные TUI-переключатели для web search, web fetch, edit/write и внешних каталогов остаются определяющим выбором политики.

### Как работает глубокий анализ

Ожидается, что типичный запуск `/repo-review`:

1. фиксирует точный `HEAD`, dirty state и запрошенные scope/ref;
2. читает авторитетные источники проекта, такие как `AGENTS.md`, README, ADR, manifests, CI и build/test scripts;
3. вызывает детерминированную инвентаризацию репозитория до широкого чтения;
4. картирует авторитетные точки входа и границы компонентов;
5. делегирует независимые ограниченные срезы scout-агентам, когда это полезно;
6. выполняет проходы по компонентам и сквозным аспектам;
7. повторно открывает точный текущий исходник перед принятием существенного дефекта;
8. записывает находки с диапазонами исходников и идентичностью blob/worktree;
9. ставит контрольные точки после существенных фаз;
10. сохраняет итоговый отчёт с явными scope, выполненными проверками, находками и ограничениями.

Для ревью PR/range дисциплина CodeSleuth явно следует за изменениями в **неизменённых** потребителей, зависимости, тесты, миграции, документацию и CI. Проверка только текстового diff не считается достаточной для глубокого ревью.

### Что ищет анализ

Встроенный протокол ревью отдельно обращает внимание на:

- канонические и производные данные, identity/provenance;
- validation и поведение fail-open/fail-closed;
- распространение ошибок и частичные отказы;
- retries, idempotency, recovery и переходы состояния;
- конкурентность, гонки и устаревшее состояние;
- authorization, изоляцию tenant/scope и secrets;
- persistence и границы транзакций;
- миграции и совместимость;
- контракты API/schema и downstream consumers;
- pagination, truncation, ограничения ресурсов и большие входы;
- adversarial-тесты вместо только happy-path тестов;
- соответствие локальной и CI-верификации;
- соответствие документации runtime-истине.

### Устойчивое состояние и compaction контекста

Состояние ревью находится в:

```text
.opencode/state/reviews/
```

Проверенные пути привязаны к идентичности содержимого. Если исходник меняется, устаревшее доказательство можно обнаружить вместо его молчаливого повторного использования.

Плагин review-compaction может восстановить ограниченную контрольную точку продолжения после compaction хоста. Цель — продолжить с записанного `next`, а не заново начинать обнаружение репозитория из-за сокращения чата.

### Отчёты

Аналитические отчёты находятся в:

```text
.codesleuth/reports/
```

Ожидаемое содержимое отчёта включает identity цели, scope, находки с расположением в исходниках, проверенные пути, реально выполненные проверки, рекомендации и ограничения. `INDEX.md` — локальный каталог.

По умолчанию отчёты остаются только локальными, потому что могут содержать фрагменты исходников, диагностику или credentials. `.codesleuth/reports/README.md` может намеренно отслеживаться для распространения соглашения.

### Производная навигация Mermaid

CodeSleuth предоставляет три намеренно разделённых представления Mermaid:

- `/repo-map` отображает ограниченный `RepositoryContextProjection` для навигации по репозиторию;
- `/repo-contracts` отображает ограниченную зависимость и обратное замыкание влияния из канонического реестра `docs/protected-capabilities.json`;
- `/eha-status` отображает ограниченную историю кампаний/SIB/исправлений из append-only журнала `eha.ndjson`.

Инструменты графа контекста поддерживают ограниченный `RepositoryContextProjection` с закрытыми словарями узлов/отношений. Элементы, взятые непосредственно из отслеживаемых исходников, могут быть помечены как verified; утверждения модели/scout-агента остаются inference. Запросы области и рендеринг Mermaid используют одни корни, hops, фильтры отношений/происхождения и границы узлов/рёбер. Метаданные выбора явно сообщают итоги и усечение, а отображённые рёбра никогда не ссылаются на пропущенные узлы.

Используйте граф для:

- навигации;
- контекста архитектуры/компонентов;
- ограниченных запросов соседства;
- выборочного восстановления контекста;
- необязательного представления Mermaid.

**Не** используйте граф или Mermaid как доказательство находки или приёмки. Существенные утверждения о репозитории по-прежнему требуют повторного открытия точного исходника и provenance blob/строка; смысл защищённых возможностей остаётся в реестре; вердикты EHA/SIB остаются в журнале и не переносятся между коммитами диаграммой.

| `/repo-map` | построение/обновление ограниченной карты архитектуры/контекста, при необходимости рендер Mermaid |
| `/repo-contracts` | просмотр реестра защищённых возможностей и ограниченный Mermaid зависимостей/влияния |
| `/eha-test` | выполнение одного изолированного уровня EHA для точного SHA кампании |
| `/eha-repair` | запись и выполнение изолированного решения об исправлении без переноса приёмки |
| `/eha-status` | просмотр авторитетного журнала EHA и его ограниченной производной Mermaid-истории |
| `/playbook` | запуск или продолжение сохранённого многошагового Playbook через изолированные Steps |

### Контроллер OpenCode `build`

Основной контроллер OpenCode — `build`. CodeSleuth не добавляет второй supervisor. Agent profile (Open-weight / Codex / Claude) выбирает модель так, чтобы использовался нативный provider prompt OpenCode; он не внедряет system prompt CodeSleuth.

```text
CodeSleuth TUI
    ↓
профиль / skill / команда / модель / разрешения
    ↓
основной OpenCode build
    ↓
нативный provider-specific controller prompt
    ↓
Задача → explore / general / Skills и субагенты CodeSleuth
```

Специфичные для CodeSleuth агенты в `.opencode/agents/` — ограниченные **субагенты**, а не заменяющие основные контроллеры.

### Внешние хосты и MCP

Текущий адаптер внешнего хоста предоставляет один репозиторий через MCP stdio с шестью инструментами доказательств только для чтения:

| Инструмент | Назначение |
| --- | --- |
| `overview` | HEAD, ветка, dirty state, количество отслеживаемых файлов и ограниченная форма репозитория |
| `inventory` | курсорная инвентаризация отслеживаемых файлов с идентичностью index blob |
| `read_evidence` | точные ограниченные строки исходников с identity working/index blob |
| `search` | ограниченный Git grep с путём, строкой и текстом |
| `test_map` | вероятные поверхности test/build/CI; явно **не** покрытие |
| `diff_evidence` | ограниченный staged/unstaged diff, привязанный к текущему HEAD |

Адаптер отклоняет path traversal, чтение untracked-файлов, symlinks/gitlinks, нерегулярные записи, неразрешённые стадии index и чтение бинарных исходников. Git-пробы усилены так, чтобы оставаться неинтерактивными/только для чтения на границе доказательств. См. [`docs/NOVACLAW-MCP.md`](docs/NOVACLAW-MCP.md).

### Состояния lifecycle

Установка runtime и зависимость исходников независимы. Контракт lifecycle включает:

- `unbound-inactive` — нет runtime и нет отслеживаемой зависимости CodeSleuth;
- `unbound-active` — runtime установлен, отслеживаемой зависимости нет;
- `bound-active` — runtime установлен и точный commit CodeSleuth зафиксирован;
- `dependency-only` / bound-inactive — зависимость сохранена, runtime отсутствует;
- `uninstalled-preserved` — runtime удалён, известные следы локально архивированы;
- `uninstalled-purged` — runtime/dependency/обычные следы удалены после безопасного при конфликтах восстановления.

Авторитетные правила restore/binding см. в [`docs/PROJECT-LIFECYCLE.md`](docs/PROJECT-LIFECYCLE.md).

### Сообщения пути обновления

| Форма сообщения | Значение |
| --- | --- |
| `source checkout: origin/main` | CodeSleuth управляет собственным checkout исходников; Check Updates/Update явно получает актуальный `origin/main` |
| `floating: <remote> <ref>` | установленная цель может использовать записанные floating-метаданные источника |
| `pinned: advance/revert the gitlink...` | проект использует точную зависимость `tools/codesleuth`; обновляйте gitlink намеренно |
| `unavailable: no explicit floating source ref` | безопасный автоматический источник полномочий на обновление не записан |

Для собственного checkout исходников CodeSleuth **Update не доверяет локальной конфигурации отслеживания ветки**. Он явно получает `origin/main` и выполняет только fast-forward чистой локальной ветки `main`. Это не позволяет устаревшей конфигурации `branch.main.merge` перенаправить обновление на удалённую feature-ветку.

### Недавняя активность

`Recent activity` содержит вывод действий control-shell, таких как Verify, update и uninstall. В новой TUI-сессии он сообщает, что ни одно управляющее действие CodeSleuth ещё не запускалось. Считайте это журналом оператора, а не отчётом анализа репозитория.

| Переменная | Владелец / использование | Пользовательская? |
| --- | --- | --- |

# Расширение CodeSleuth

## Что можно расширять?

Принятые точки расширения:

```text
профили
Skills
Playbooks / команды
небольшие инструменты
плагины
ограниченные субагенты
адаптеры / коннекторы хостов
UX управления расширениями
```

Следующее **не** является точками расширения без нового архитектурного решения:

```text
вторая среда выполнения модели
второй основной контроллер
независимый цикл агента
независимый универсальный маршрутизатор инструментов
заменяющий движок ревью
второе каноническое хранилище истины репозитория
```

## Текущий workflow расширений

Полного TUI package manager пока нет. Сегодня загрузка расширений в основном нативная для хоста/ручная, а TUI CodeSleuth обнаруживает установленные команды, Skills, tools и plugins.

Для интеграции OpenCode распространяемый материал находится в:

```text
pack/.opencode/
├── agents/
├── commands/
├── plugins/
├── profiles/
├── skills/
└── tools/
```

Installer материализует pack в дерево `.opencode/` целевого репозитория, сохраняя пользовательскую конфигурацию в соответствии с контрактом lifecycle/update.

### Добавление Skill

Используйте существующий каталог Skill как шаблон:

```text
.opencode/skills/<skill-name>/SKILL.md
```

Текущие Skills используют YAML frontmatter как минимум с:

```yaml
---
name: skill-name
description: What the skill does
---
```

Skill должен определять переиспользуемое поведение и инварианты, а не заменять контроллер хоста. Если он записывает производное состояние, документируйте канонический вход и правило invalidation/rebuild.

### Добавление команды OpenCode / точки входа Playbook

Файлы команд находятся в:

```text
.opencode/commands/<command>.md
```

Текущие команды CodeSleuth объявляют `agent: build` и направляют задачу в Skills/tools, а не создают нового основного агента. Используйте существующие файлы команд `/repo-*` как шаблоны.

### Добавление ограниченного субагента

Определения субагентов OpenCode находятся в:

```text
.opencode/agents/<name>.md
```

Специализированные агенты CodeSleuth имеют `mode: subagent`. Держите scope и разрешения ограниченными. `repo-scout` — эталон read-only специалиста, возвращающего кандидатные доказательства для верификации родителем.

### Добавление инструмента

Нативные инструменты OpenCode находятся в:

```text
.opencode/tools/
```

Текущие примеры:

```text
repo_inventory.ts
repo_profile.ts
review_state.ts
repo_context_graph.ts
```

Предпочитайте небольшой инструмент, предоставляющий детерминированное и полезное хосту поведение. Не пересоздавайте возможность, которой хост уже владеет.

### Добавление плагина

Локальный код плагинов находится в `.opencode/plugins/`; пакетные плагины также могут объявляться через конфигурацию хоста. `review-compaction.ts` — текущий локальный пример. Пакет keepalive настраивается через `opencode.json`/runtime-настройки CodeSleuth.

Плагины остаются нативным выполнением хоста. CodeSleuth может настраивать или упаковывать их, но не становится их runtime.

### Добавление профиля репозитория

Файлы встроенных профилей находятся в:

```text
.opencode/profiles/builtin/<profile>.json
```

Профиль может описывать:

- доказательства определения;
- наследуемый профиль (`extends`);
- рекомендуемую верификацию;
- фокус ревью;
- совместимые значения конфигурации по умолчанию.

`repo_profile` разрешает `extends` только внутри установленного канонического каталога `.opencode/profiles/builtin/`. Родители объединяются перед потомками, ключи объектов объединяются рекурсивно, массивы дедуплицируются в стабильном порядке, а отсутствующие родители или циклы приводят к закрытому отказу. Исторические копии профилей верхнего уровня не являются вторым источником полномочий.

**Важно:** добавления нового файла профиля недостаточно, чтобы сегодня сделать его первоклассным TUI-профилем. Текущие validation/detection явно знают `generic`, `rust`, `python`, `node` и `typescript`; вклад нового встроенного профиля должен также обновить constants/detection/validation path профилей и тесты.

Профили никогда не должны молча расширять разрешения.

### Добавление интеграции хоста

Адаптер хоста должен быть настолько тонким, насколько позволяет контракт хоста. Обязательные инварианты:

1. хост сохраняет полномочия controller/model/session/tool-routing;
2. CodeSleuth не компенсирует различия хостов ростом параллельного цикла агента;
3. общие Skills/дисциплина доказательств переиспользуются там, где это практично;
4. состояние, специфичное для интеграции, не становится вторым источником истины выполнения;
5. разрешения и границы безопасности адаптера тестируются явно.

MCP-адаптер NovaClaw — текущая эталонная точка интеграции внешнего хоста.

## Классификации изменений

PR должны классифицировать себя как один из вариантов:

```text
CORE-HARDENING
PROFILE-EXTENSION
SKILL-EXTENSION
PLAYBOOK-EXTENSION
TOOL-EXTENSION
HOST-INTEGRATION
EXTENSION-MANAGEMENT-UX
DOCS
```

Изменение вне этих категорий должно до реализации объяснить, почему оно не нарушает архитектуру с замороженным core.

## Development-gates

Установите Python-зависимости разработки:

```bash
python -m pip install -r requirements-dev.txt
```

Запустите Python suite и lint:

```bash
python -m pytest
ruff check .
```

Запустите smokes устойчивого состояния/графа контекста:

```bash
bun install --frozen-lockfile
bun tests/review_state_smoke.ts
bun tests/context_graph_smoke.ts
```

Если изменялся MCP:

```bash
python -m pip install -r requirements-mcp.txt
python -m pytest -q tests/test_mcp_server.py
ruff check codesleuth_mcp tests/test_mcp_server.py
```

Изменения TUI следует тестировать headless-покрытием `App.run_test()`/Pilot Textual на узких и широких viewport, а затем проверять в реальном терминале. Изменения lifecycle должны использовать реальные одноразовые Git-репозитории/submodules, а не замокивать поведение, которое требуется защитить.

## Правило документации

Документация прежде всего текстовая и terminal-native.

- Копируйте канонический ASCII-бренд из `CODESLEUTH_ART`; не перерисовывайте его многократно.
- Руководства по UI должны описывать точные реализованные labels и использовать реальные terminal snapshots, когда snapshot нужен.
- Не поддерживайте PNG/JPEG/WebP/SVG mockups UI или reference boards.
- Mermaid — разрешённый формат диаграмм, когда полезны закодированные отношения; сгенерированный Mermaid остаётся представлением, а не истиной репозитория.

# Дорожная карта и задачи

Направление — **независимый от агентов CodeSleuth с небольшим замороженным ядром**, а не более крупная среда агента CodeSleuth.

## Текущий трек усиления

Перед расширением интеграций текущая линия 0.3 сосредоточена на:

- удобстве TUI и поведении viewport;
- корректности lifecycle/update;
- обратимом сохранении конфигурации;
- безопасности детерминированных доказательств;
- корректности устойчивого состояния/графа контекста;
- согласованности документации и runtime;
- regression-покрытии реального поведения Git;
- добавлении CI вокруг уже определённых acceptance-gates.

## Направление независимости от хоста

Планируемая последовательность:

1. **Сохранять OpenCode production-надёжным.** Он остаётся текущей полной установленной эталонной интеграцией.
2. **Сохранять MCP NovaClaw узким и доказанным.** Он показывает, что доказательства CodeSleuth можно потреблять без владения средой агента со стороны CodeSleuth.
3. **Отделить общую дисциплину от упаковки хоста.** Skills, соглашения по доказательствам и метаданные расширений должны стать переиспользуемыми без притворства, будто все хосты предоставляют одинаковые примитивы.
4. **Добавить ранние интеграции хостов Codex и Cursor.** Каждый адаптер должен использовать нативные модели/tools/controllers хоста, а не эмулировать OpenCode внутри CodeSleuth.
5. **Добавить интеграции Hermes, BodegaOne и Pi-harness** с тем же правилом владения.
6. **Построить матрицу возможностей хостов.** Интеграция должна явно указывать, какие Skills, evidence tools, permissions и lifecycle features она действительно поддерживает.
7. **Развивать UX управления расширениями.** Discovery, provenance, compatibility, install/load, enable/disable, update и remove могут стать проще через CLI/TUI, пока выполнение остаётся нативным для хоста.
8. **Не размораживать ядро случайно.** Новая возможность обычно должна быть profile, Skill, Playbook, small tool, plugin или host adapter.

Конечное состояние намеренно скромное: CodeSleuth должен быть переиспользуемым **набором дисциплины и панелью управления** вокруг coding agents, а не ещё одним coding agent, конкурирующим с ними.

# Безопасность и локальное состояние

CodeSleuth работает через авторизованный хост. Если этот хост может запускать тесты, читать файлы, обращаться к development-сервисам или использовать developer credentials, доказательства и отчёты могут содержать эти значения. CodeSleuth **не** выполняет тотальную редакцию всего вывода, потому что это сделало бы некоторые реальные аудиты/тесты некорректными.

Поведение локального состояния по умолчанию:

- backups, archives и тела отчётов `.codesleuth/` локально исключаются через repository-local exclude-файл Git;
- `.opencode/state/`, caches, logs, sessions, snapshots, runtime dependencies и bytecode локально исключаются;
- CodeSleuth не переписывает молча отслеживаемый `.gitignore` целевого репозитория для этих patterns;
- `tools/codesleuth` намеренно не игнорируется, когда выбрана привязка зависимости;
- отчёты следует проверять/санитизировать перед намеренной публикацией;
- uninstall использует conflict-safe restore и сохраняет recovery evidence, когда изменённый пользователем ранее существовавший файл нельзя восстановить автоматически.

Точную семантику lifecycle см. в [`docs/PROJECT-LIFECYCLE.md`](docs/PROJECT-LIFECYCLE.md), а старое подробное эксплуатационное руководство, сохранённое для совместимости/справки, — в [`docs/USER-GUIDE.md`](docs/USER-GUIDE.md).
