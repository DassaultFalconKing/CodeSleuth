# CodeSleuth

```text
+-------------------------------------------------+
|  CODE:SLEUTH // EVIDENCE OPERATIONS CONSOLE    |
+----------------------+--------------------------+
                       .-""""-.
                     .'  ____  '.
                    /   /_  _\   \
                   |   |o || o|   |
                   |   |__||__|   |
                   |      /\      |
                    \   .____.   /
                 ____'.\____/.'____
               .' ___/|  /\  |\___ '.
              /__/    | /  \ |    \__\
                   [ TARGET : SOURCE ]
                   [ EVIDENCE : LIVE ]
```

**Дисципліна роботи LLM з репозиторіями коду.**

CodeSleuth — невеликий шар дисципліни для агентів програмування. Він об'єднує повторно використовувані Skills для рев'ю, профілі репозиторіїв, стійкі домовленості щодо доказів, термінальну панель керування та кілька обмежених інструментів для роботи з репозиторієм. Хост-агент і надалі володіє моделлю, контролером, сесією, дозволами, маршрутизацією інструментів і циклом виконання.

Поточна версія: **0.3.0**.

Поточна базова реалізація:

- **Update** для вихідного checkout явно отримує актуальний `origin/main` і виконує лише fast-forward чистого локального `main`, ігноруючи застарілі метадані відстеження гілки;
- активна поверхня TUI залишається у верхній частині області вмісту; великий блок бренду та нижній Footer можна приховувати незалежно один від одного;
- ліву навігацію можна згортати/відновлювати, а праву панель Keys/Help — згортати/відновлювати або закривати на поточну TUI-сесію;
- зовнішній MCP-адаптер доказів прив'язаний до репозиторію, обмежений і посилений як поверхня доказів лише для читання, а не як альтернативне середовище виконання агента.

| Поверхня | Статус |
| --- | --- |
| OpenCode | поточна повна встановлена інтеграція хоста |
| NovaClaw | поточний зовнішній хост через MCP-докази лише для читання |
| Codex, Cursor, Hermes, BodegaOne, Pi-harness | заплановані цілі інтеграції хостів після посилення |
| Середовище виконання моделі / supervisor, що належить CodeSleuth | навмисно не є частиною продукту |

# Основи

## Яку проблему вирішує CodeSleuth?

LLM добре читають код, але робота з великими репозиторіями зазнає невдач дуже передбачуваними способами:

- репозиторій більший за корисний робочий контекст моделі;
- знайти файли — не те саме, що зрозуміти їх;
- підсумок scout-агента або субагента може бути помилковим;
- довге рев'ю може втратити стан після compaction або в новій сесії;
- PR може виглядати коректно локально, водночас ламаючи незміненого викликача, схему, міграцію, тест або експлуатаційний контракт;
- агенти часто заявляють більше покриття, ніж фактично виконали.

CodeSleuth дає хост-агенту повторювану дисципліну для цих проблем:

```text
репозиторій
  -> детермінована інвентаризація
  -> обмежена перевірка
  -> карта архітектури/контексту
  -> точні докази з вихідного коду
  -> верифікація
  -> знахідка/звіт/контрольна точка
```

Просте правило: **виявляй широко, перевіряй вузько й зберігай те, що важливо.**

## Що він уміє сьогодні?

CodeSleuth підтримує:

- рев'ю всього репозиторію;
- рев'ю великих PR або діапазонів комітів;
- побудову карт архітектури й компонентів;
- документацію репозиторію, виведену з поточного коду/конфігурації/тестів;
- рев'ю контрактів коду та API/схем;
- перевірку узгодженості тестів/CI/документації;
- проходи щодо безпеки, авторизації, області дії, стану, відновлення, конкурентності, персистентності та міграцій;
- рев'ю з обмеженнями ресурсів і великих вхідних даних;
- відновлювані рев'ю зі стійкими знахідками та контрольними точками;
- профілі репозиторіїв для фокуса й рекомендацій щодо верифікації, специфічних для мови/фреймворку;
- локальні аналітичні звіти, придатні для повторного використання наступними сесіями в тому самому worktree;
- обмежені проєкції контексту з необов'язковим рендерингом Mermaid;
- докази репозиторію лише для читання для зовнішніх MCP-хостів;
- оборотні install/update/uninstall і необов'язкову фіксацію залежності на точній версії.

Він робить це **не замінюючи моделі, агентів, інструменти та команди OpenCode** або еквівалентні засоби середовища виконання іншого хоста.

## Чого він не робить?

CodeSleuth — це не:

- середовище виконання моделі;
- універсальний supervisor агентів;
- другий маршрутизатор інструментів;
- незалежний замінний рушій рев'ю;
- магічний оракул покриття;
- причина довіряти згенерованій діаграмі або підсумку scout-агента як доказу;
- поки що не менеджер пакетів для довільних розширень.

Ядро навмисно мале. Зростання має відбуватися у Skills, профілях, Playbooks, інструментах, плагінах та адаптерах хостів.

## Поточна модель виконання

Для встановленої інтеграції OpenCode:

```text
CodeSleuth -> конфігурація / Skills / профілі / дисципліна доказів / TUI
OpenCode   -> модель / контролер / агенти / інструменти / виконання
```

Для зовнішнього хоста:

```text
CodeSleuth -> підтримувані Skills та/або вузькі інтерфейси доказів
Хост       -> модель / контролер / дозволи / інструменти / виконання
```

Хост завжди залишається джерелом повноважень на виконання.

# Посібник користувача

## Швидкий старт

### Вимоги

Для поточної повної інтеграції OpenCode:

- Git **2.35+**;
- Python **3.10+**;
- OpenCode, доступний як `opencode`;
- необов'язково Bun для запуску development-gates стану/графа контексту на TypeScript.

TUI використовує `textual==8.2.8` в ізольованому середовищі виконання, якщо Textual саме цієї версії ще недоступний.

### Запуск TUI з checkout CodeSleuth

Linux/macOS/WSL:

```bash
./codesleuth /path/to/project
```

PowerShell:

```powershell
.\codesleuth.ps1 C:\path\to\project
```

Допускається вкладений шлях; CodeSleuth нормалізує його до кореня Git-репозиторію, що його містить.

### Перший запуск

1. Відкрийте **Configure**.
2. Виберіть поведінку install/update/adopt.
3. Залиште автоматичне визначення профілю репозиторію, якщо тільки репозиторій не є незвичним або змішаним.
4. Виберіть preset дозволів. `review-safe` — значення за замовчуванням із мінімальними привілеями.
5. За потреби виберіть Agent profile/model для інтеграції OpenCode.
6. Застосуйте конфігурацію.
7. Запустіть **Verify**.
8. Виберіть **Open CodeSleuth**, щоб запустити налаштоване середовище OpenCode.
9. В OpenCode почніть із `/repo-prompts` для поради щодо завдання або з `/repo-review` для повного evidence-first рев'ю.

Для прямого неінтерактивного встановлення:

```bash
./install.sh /path/to/project
```

PowerShell:

```powershell
.\install.ps1 C:\path\to\project
```

Для проєкту, який має записувати точну ревізію вихідного коду CodeSleuth як Git-залежність:

```bash
./install.sh /path/to/project --bind-dependency
```

Це додає до staging `.gitmodules` і gitlink `tools/codesleuth`. CodeSleuth **не** виконує commit або push цільового репозиторію.

## Докладно

### Важливі терміни

| Термін | Значення |
| --- | --- |
| **Host** | Реальне середовище coding-agent. Воно володіє сесією моделі, контролером, маршрутизацією інструментів і виконанням. OpenCode — поточний повний хост; NovaClaw — перший зовнішній MCP-хост. |
| **Skill** | Повторно використовуваний пакет протоколу/інструкцій, що визначає, як хост має виконувати певний клас роботи. |
| **Command** | Користувацька команда хоста, яка спрямовує роботу в Skill або workflow. В OpenCode це команди `/repo-*`. |
| **Playbook** | Готовий до запуску рецепт завдання, згенерований для конкретного репозиторію/завдання. Це рецепт prompt, а не Skill. |
| **Profile** | Метадані типу репозиторію: докази визначення, фокус рев'ю, значення конфігурації за замовчуванням і рекомендована верифікація. Профілі не надають дозволів. |
| **Agent profile** | Специфічний для OpenCode вибір сімейства моделей (`native`, `open-weight`, `codex`, `claude`). Він не встановлює supervisor prompt CodeSleuth. |
| **Tool** | Невелика виконувана можливість, наприклад детермінована інвентаризація, стійкий стан рев'ю або операції графа контексту. |
| **Plugin** | Нативна інтеграція хоста, яку завантажує хост, наприклад підтримка review-compaction. |
| **Review state** | Локальний структурований стан продовження в `.opencode/state/`, що використовується для безпечного відновлення після compaction/переривання сесії. |
| **Report** | Markdown у `.codesleuth/reports/`, читабельний людиною/асистентом. Звіти підсумовують роботу; вони не є runtime-станом. |
| **Context graph** | Обмежена похідна проєкція репозиторію для навігації/контексту. Вона перебудовується й ніколи не є сильнішим доказом, ніж вихідний код. |

### Вбудовані Skills

Поточні розповсюджувані Skills містяться в `pack/.opencode/skills/`:

- **`repository-deep-review`** — картування великих репозиторіїв, документація, рев'ю всього репозиторію та великих PR зі стійкими контрольними точками;
- **`codesleuth-reports`** — записує й підтримує аналітичні звіти в `.codesleuth/reports/`;
- **`feature-porting-discipline`** — evidence-first перенесення можливостей між репозиторіями без копіювання архітектури, специфічної для джерела, і без створення дублюючої runtime-влади.

Протокол deep-review має кілька правил, що не підлягають обговоренню:

1. контекст — це робоча пам'ять, а не репозиторій;
2. inventory/discovery — не семантичне покриття;
3. підсумки scout-агентів — зачіпки, а не знахідки;
4. суттєві знахідки потребують точних доказів із поточного вихідного коду;
5. продовженням володіє стійкий стан, а не історія чату;
6. тест/перевірка вважається пройденою лише якщо вона справді успішно виконувалась;
7. агент перевіряє реально запитаний HEAD/range/worktree, а не застарілий підсумок.

### Вбудовані профілі репозиторіїв

Поточні вбудовані профілі:

```text
generic
rust
python
node
typescript
```

Автоматичне визначення профілю використовує **відстежувані Git-файли**, а не довільний вміст файлової системи. Приклади:

- `Cargo.toml` / відстежувані `.rs` -> Rust;
- `pyproject.toml`, `requirements.txt`, `setup.py` або відстежувані `.py` -> Python;
- `package.json` -> Node;
- `tsconfig*.json`, відстежувані `.ts` / `.tsx` -> TypeScript.

Профілі можуть додавати фокус рев'ю та рекомендації щодо верифікації. Вони **не** розширюють мовчки дозволи на web, edit, shell або зовнішні каталоги.

### Preset-и дозволів

TUI надає три preset-и:

| Preset | Призначення |
| --- | --- |
| `review-safe` | мінімальні привілеї; безпечна Git-інспекція дозволена, а широкі shell/edit/web-дії залишаються контрольованими |
| `balanced` | додатково дозволяє звичайні команди верифікації проєкту, як-от pytest, cargo tests/checks і команди lint/typecheck/test менеджерів пакетів |
| `autonomous` | широко дозволяє shell-роботу, водночас продовжує питати перед руйнівними/публікуючими Git-діями, як-от push/reset/clean |

Явні TUI-перемикачі для web search, web fetch, edit/write і зовнішніх каталогів залишаються визначальним вибором політики.

### Як працює глибокий аналіз

Очікується, що типовий запуск `/repo-review`:

1. фіксує точний `HEAD`, dirty state і запитані scope/ref;
2. читає авторитетні джерела проєкту, як-от `AGENTS.md`, README, ADR, manifests, CI і build/test scripts;
3. викликає детерміновану інвентаризацію репозиторію до широкого читання;
4. картує авторитетні точки входу й межі компонентів;
5. делегує незалежні обмежені зрізи scout-агентам, коли це корисно;
6. виконує проходи за компонентами та наскрізними аспектами;
7. повторно відкриває точний поточний вихідний код перед прийняттям суттєвого дефекту;
8. записує знахідки з діапазонами вихідного коду та ідентичністю blob/worktree;
9. ставить контрольні точки після суттєвих фаз;
10. зберігає підсумковий звіт із явними scope, виконаними перевірками, знахідками й обмеженнями.

Для рев'ю PR/range дисципліна CodeSleuth явно простежує зміни в **незмінених** споживачів, залежності, тести, міграції, документацію та CI. Перевірка лише текстового diff не вважається достатньою для глибокого рев'ю.

### Що шукає аналіз

Вбудований протокол рев'ю окремо звертає увагу на:

- канонічні та похідні дані, identity/provenance;
- validation і поведінку fail-open/fail-closed;
- поширення помилок і часткові відмови;
- retries, idempotency, recovery і переходи стану;
- конкурентність, гонки та застарілий стан;
- authorization, ізоляцію tenant/scope і secrets;
- persistence і межі транзакцій;
- міграції та сумісність;
- контракти API/schema і downstream consumers;
- pagination, truncation, обмеження ресурсів і великі входи;
- adversarial-тести замість лише happy-path тестів;
- відповідність локальної та CI-верифікації;
- відповідність документації runtime-істині.

### Стійкий стан і compaction контексту

Стан рев'ю міститься в:

```text
.opencode/state/reviews/
```

Перевірені шляхи прив'язані до ідентичності вмісту. Якщо вихідний код змінюється, застарілий доказ можна виявити замість його мовчазного повторного використання.

Плагін review-compaction може відновити обмежену контрольну точку продовження після compaction хоста. Мета — продовжити із записаного `next`, а не заново починати виявлення репозиторію через скорочення чату.

### Звіти

Аналітичні звіти містяться в:

```text
.codesleuth/reports/
```

Очікуваний вміст звіту включає identity цілі, scope, знахідки з розташуванням у вихідному коді, перевірені шляхи, реально виконані перевірки, рекомендації та обмеження. `INDEX.md` — локальний каталог.

За замовчуванням звіти залишаються лише локальними, оскільки можуть містити фрагменти вихідного коду, діагностику або credentials. `.codesleuth/reports/README.md` може навмисно відстежуватися для поширення домовленості.

### Граф контексту репозиторію та Mermaid

Інструменти графа контексту підтримують обмежений `RepositoryContextProjection` із закритими словниками вузлів/відношень. Елементи, отримані безпосередньо з відстежуваного вихідного коду, можуть бути позначені як verified; твердження моделі/scout-агента залишаються inference.

Використовуйте граф для:

- навігації;
- контексту архітектури/компонентів;
- обмежених запитів сусідства;
- вибіркового відновлення контексту;
- необов'язкового представлення Mermaid.

**Не** використовуйте граф або Mermaid як доказ знахідки. Суттєві твердження й надалі потребують повторного відкриття точного вихідного коду.

### Команди OpenCode

Поточні встановлені команди:

| Команда | Призначення |
| --- | --- |
| `/repo-prompts` | радник щодо завдань / рекомендована наступна робота з репозиторієм |
| `/repo-profile` | перевірка або виведення інформації про профіль репозиторію |
| `/repo-review` | глибоке evidence-first рев'ю репозиторію або PR |
| `/repo-review-resume` | продовження стійкого рев'ю |
| `/repo-docs` | створення evidence-first документації репозиторію |
| `/repo-report` | збереження матеріалу аналітичного звіту |
| `/repo-map` | побудова/оновлення обмеженої карти архітектури/контексту, за потреби рендер Mermaid |

### Контролер OpenCode `build`

Основний контролер OpenCode — `build`. CodeSleuth не додає другий supervisor. Agent profile (Open-weight / Codex / Claude) вибирає модель так, щоб використовувався нативний provider prompt OpenCode; він не впроваджує system prompt CodeSleuth.

```text
CodeSleuth TUI
    ↓
профіль / skill / команда / модель / дозволи
    ↓
основний OpenCode build
    ↓
нативний provider-specific controller prompt
    ↓
Завдання → explore / general / Skills і субагенти CodeSleuth
```

Специфічні для CodeSleuth агенти в `.opencode/agents/` — обмежені **субагенти**, а не замінні основні контролери.

### Зовнішні хости та MCP

Поточний адаптер зовнішнього хоста надає один репозиторій через MCP stdio із шістьма інструментами доказів лише для читання:

| Інструмент | Призначення |
| --- | --- |
| `overview` | HEAD, гілка, dirty state, кількість відстежуваних файлів та обмежена форма репозиторію |
| `inventory` | курсорна інвентаризація відстежуваних файлів з ідентичністю index blob |
| `read_evidence` | точні обмежені рядки вихідного коду з identity working/index blob |
| `search` | обмежений Git grep зі шляхом, рядком і текстом |
| `test_map` | імовірні поверхні test/build/CI; явно **не** покриття |
| `diff_evidence` | обмежений staged/unstaged diff, прив'язаний до поточного HEAD |

Адаптер відхиляє path traversal, читання untracked-файлів, symlinks/gitlinks, нерегулярні записи, нерозв'язані стадії index і читання бінарного вихідного коду. Git-проби посилені так, щоб залишатися неінтерактивними/лише для читання на межі доказів. Див. [`docs/NOVACLAW-MCP.md`](docs/NOVACLAW-MCP.md).

### Стани lifecycle

Встановлення runtime і залежність вихідного коду незалежні. Контракт lifecycle включає:

- `unbound-inactive` — немає runtime і немає відстежуваної залежності CodeSleuth;
- `unbound-active` — runtime встановлено, відстежуваної залежності немає;
- `bound-active` — runtime встановлено й точний commit CodeSleuth зафіксовано;
- `dependency-only` / bound-inactive — залежність збережена, runtime відсутній;
- `uninstalled-preserved` — runtime видалено, відомі сліди локально заархівовано;
- `uninstalled-purged` — runtime/dependency/звичайні сліди видалено після безпечного за конфліктів відновлення.

Авторитетні правила restore/binding див. у [`docs/PROJECT-LIFECYCLE.md`](docs/PROJECT-LIFECYCLE.md).

### Повідомлення шляху оновлення

| Форма повідомлення | Значення |
| --- | --- |
| `source checkout: origin/main` | CodeSleuth керує власним checkout вихідного коду; Check Updates/Update явно отримує актуальний `origin/main` |
| `floating: <remote> <ref>` | встановлена ціль може використовувати записані floating-метадані джерела |
| `pinned: advance/revert the gitlink...` | проєкт використовує точну залежність `tools/codesleuth`; оновлюйте gitlink навмисно |
| `unavailable: no explicit floating source ref` | безпечне автоматичне джерело повноважень на оновлення не записане |

Для власного checkout вихідного коду CodeSleuth **Update не довіряє локальній конфігурації відстеження гілки**. Він явно отримує `origin/main` і виконує лише fast-forward чистої локальної гілки `main`. Це не дозволяє застарілій конфігурації `branch.main.merge` перенаправити оновлення на видалену feature-гілку.

### Нещодавня активність

`Recent activity` містить вивід дій control-shell, як-от Verify, update і uninstall. У новій TUI-сесії він повідомляє, що жодна керуюча дія CodeSleuth ще не запускалась. Вважайте це журналом оператора, а не звітом аналізу репозиторію.

### Екран Configure

Екран конфігурації керує:

1. install/update/adoption legacy-встановлення та необов'язковим прив'язуванням залежності;
2. автоматичним визначенням профілю репозиторію або ручним вибором;
3. OpenCode Agent profile і необов'язковим model id;
4. явними дозволами evidence/web/edit/external-directory;
5. Exa, keepalive, лімітами stall/recovery, резервом compaction і перевірками оновлень;
6. результуючим підсумком запланованої політики.

**Apply** записує вибрану конфігурацію. **Cancel**, **Back** або Escape переривають дію без застосування.

## Довідник змінних середовища

CodeSleuth навмисно має невелику поверхню середовища.

| Змінна | Власник / використання | Користувацька? |
| --- | --- | --- |
| `OPENCODE_ENABLE_EXA` | встановлений launcher OpenCode задає/знімає її з runtime-налаштувань CodeSleuth | зазвичай керується CodeSleuth |

| `REVIEW_PACK_TARGET_ROOT` | встановлений TUI/bootstrap визначає цільовий репозиторій | внутрішнє compatibility-ім'я |

# Розширення CodeSleuth

## Що можна розширювати?

Прийняті точки розширення:

```text
профілі
Skills
Playbooks / команди
невеликі інструменти
плагіни
обмежені субагенти
адаптери / конектори хостів
UX керування розширеннями
```

Наведене нижче **не** є точками розширення без нового архітектурного рішення:

```text
друге середовище виконання моделі
другий основний контролер
незалежний цикл агента
незалежний універсальний маршрутизатор інструментів
замінний рушій рев'ю
друге канонічне сховище істини репозиторію
```

## Поточний workflow розширень

Повного TUI package manager поки немає. Сьогодні завантаження розширень переважно нативне для хоста/ручне, а TUI CodeSleuth виявляє встановлені команди, Skills, tools і plugins.

Для інтеграції OpenCode розповсюджуваний матеріал міститься в:

```text
pack/.opencode/
├── agents/
├── commands/
├── plugins/
├── profiles/
├── skills/
└── tools/
```

Installer матеріалізує pack у дерево `.opencode/` цільового репозиторію, зберігаючи користувацьку конфігурацію відповідно до контракту lifecycle/update.

### Додавання Skill

Використовуйте наявний каталог Skill як шаблон:

```text
.opencode/skills/<skill-name>/SKILL.md
```

Поточні Skills використовують YAML frontmatter щонайменше з:

```yaml
---
name: skill-name
description: What the skill does
---
```

Skill має визначати повторно використовувану поведінку та інваріанти, а не замінювати контролер хоста. Якщо він записує похідний стан, документуйте канонічний вхід і правило invalidation/rebuild.

### Додавання команди OpenCode / точки входу Playbook

Файли команд містяться в:

```text
.opencode/commands/<command>.md
```

Поточні команди CodeSleuth оголошують `agent: build` і спрямовують завдання в Skills/tools, а не створюють нового основного агента. Використовуйте наявні файли команд `/repo-*` як шаблони.

### Додавання обмеженого субагента

Визначення субагентів OpenCode містяться в:

```text
.opencode/agents/<name>.md
```

Спеціалізовані агенти CodeSleuth мають `mode: subagent`. Тримайте scope і дозволи обмеженими. `repo-scout` — еталон read-only спеціаліста, який повертає кандидатні докази для верифікації батьківським агентом.

### Додавання інструмента

Нативні інструменти OpenCode містяться в:

```text
.opencode/tools/
```

Поточні приклади:

```text
repo_inventory.ts
repo_profile.ts
review_state.ts
repo_context_graph.ts
```

Віддавайте перевагу невеликому інструменту, що надає детерміновану й корисну хосту поведінку. Не відтворюйте можливість, якою хост уже володіє.

### Додавання плагіна

Локальний код плагінів міститься в `.opencode/plugins/`; пакетні плагіни також можуть оголошуватися через конфігурацію хоста. `review-compaction.ts` — поточний локальний приклад. Пакет keepalive налаштовується через `opencode.json`/runtime-налаштування CodeSleuth.

Плагіни залишаються нативним виконанням хоста. CodeSleuth може налаштовувати або пакувати їх, але не стає їхнім runtime.

### Додавання профілю репозиторію

Файли вбудованих профілів містяться в:

```text
.opencode/profiles/builtin/<profile>.json
```

Профіль може описувати:

- докази визначення;
- успадкований профіль (`extends`);
- рекомендовану верифікацію;
- фокус рев'ю;
- сумісні значення конфігурації за замовчуванням.

**Важливо:** додавання нового файлу профілю недостатньо, щоб сьогодні зробити його повноцінним TUI-профілем. Поточні validation/detection явно знають `generic`, `rust`, `python`, `node` і `typescript`; внесок нового вбудованого профілю має також оновити constants/detection/validation path профілів і тести.

Профілі ніколи не повинні мовчки розширювати дозволи.

### Додавання інтеграції хоста

Адаптер хоста має бути настільки тонким, наскільки дозволяє контракт хоста. Обов'язкові інваріанти:

1. хост зберігає повноваження controller/model/session/tool-routing;
2. CodeSleuth не компенсує відмінності хостів зростанням паралельного циклу агента;
3. спільні Skills/дисципліна доказів повторно використовуються там, де це практично;
4. стан, специфічний для інтеграції, не стає другим джерелом істини виконання;
5. дозволи та межі безпеки адаптера тестуються явно.

MCP-адаптер NovaClaw — поточна еталонна точка інтеграції зовнішнього хоста.

## Класифікації змін

PR мають класифікувати себе як один із варіантів:

```text
CORE-HARDENING
PROFILE-EXTENSION
SKILL-EXTENSION
PLAYBOOK-EXTENSION
TOOL-EXTENSION
HOST-INTEGRATION
EXTENSION-MANAGEMENT-UX

```

Зміна поза цими категоріями має до реалізації пояснити, чому вона не порушує архітектуру із замороженим core.

## Development-gates

Встановіть Python-залежності розробки:

```bash
python -m pip install -r requirements-dev.txt
```

Запустіть Python suite і lint:

```bash
python -m pytest
ruff check .
```

Запустіть smokes стійкого стану/графа контексту:

```bash
bun install --frozen-lockfile
bun tests/review_state_smoke.ts
bun tests/context_graph_smoke.ts
```

Якщо змінювався MCP:

```bash
python -m pip install -r requirements-mcp.txt
python -m pytest -q tests/test_mcp_server.py
ruff check codesleuth_mcp tests/test_mcp_server.py
```

Зміни TUI слід тестувати headless-покриттям `App.run_test()`/Pilot Textual на вузьких і широких viewport, а потім перевіряти в реальному терміналі. Зміни lifecycle мають використовувати реальні одноразові Git-репозиторії/submodules, а не замокувати поведінку, яку потрібно захистити.

## Правило документації

Документація передусім текстова та terminal-native.

- Копіюйте канонічний ASCII-бренд із `CODESLEUTH_ART`; не перемальовуйте його багаторазово.
- Посібники з UI мають описувати точні реалізовані labels і використовувати реальні terminal snapshots, коли snapshot потрібен.
- Не підтримуйте PNG/JPEG/WebP/SVG mockups UI або reference boards.
- Mermaid — дозволений формат діаграм, коли корисні закодовані відношення; згенерований Mermaid залишається представленням, а не істиною репозиторію.

# Дорожня карта та завдання

Напрям — **незалежний від агентів CodeSleuth із невеликим замороженим ядром**, а не більший runtime агента CodeSleuth.

## Поточний трек посилення

Перед розширенням інтеграцій поточна лінія 0.3 зосереджена на:

- зручності TUI і поведінці viewport;
- коректності lifecycle/update;
- оборотному збереженні конфігурації;
- безпеці детермінованих доказів;
- коректності стійкого стану/графа контексту;
- узгодженості документації та runtime;
- regression-покритті реальної поведінки Git;
- додаванні CI навколо вже визначених acceptance-gates.

## Напрям незалежності від хоста

Запланована послідовність:

1. **Зберігати OpenCode production-надійним.** Він залишається поточною повною встановленою еталонною інтеграцією.
2. **Зберігати MCP NovaClaw вузьким і доведеним.** Він показує, що докази CodeSleuth можна споживати без володіння середовищем агента з боку CodeSleuth.
3. **Відокремити спільну дисципліну від пакування хоста.** Skills, домовленості щодо доказів і метадані розширень мають стати повторно використовуваними без удавання, ніби всі хости надають однакові примітиви.
4. **Додати ранні інтеграції хостів Codex і Cursor.** Кожен адаптер має використовувати нативні моделі/tools/controllers хоста, а не емулювати OpenCode всередині CodeSleuth.
5. **Додати інтеграції Hermes, BodegaOne і Pi-harness** із тим самим правилом володіння.
6. **Побудувати матрицю можливостей хостів.** Інтеграція має явно вказувати, які Skills, evidence tools, permissions і lifecycle features вона справді підтримує.
7. **Розвивати UX керування розширеннями.** Discovery, provenance, compatibility, install/load, enable/disable, update і remove можуть стати простішими через CLI/TUI, поки виконання залишається нативним для хоста.
8. **Не розморожувати ядро випадково.** Нова можливість зазвичай має бути profile, Skill, Playbook, small tool, plugin або host adapter.

Кінцевий стан навмисно скромний: CodeSleuth має бути повторно використовуваним **набором дисципліни та панеллю керування** навколо coding agents, а не ще одним coding agent, що конкурує з ними.

# Безпека та локальний стан

CodeSleuth працює через авторизований хост. Якщо цей хост може запускати тести, читати файли, звертатися до development-сервісів або використовувати developer credentials, докази та звіти можуть містити ці значення. CodeSleuth **не** виконує суцільну редакцію всього виводу, оскільки це зробило б деякі реальні аудити/тести некоректними.

Поведінка локального стану за замовчуванням:

- backups, archives і тіла звітів `.codesleuth/` локально виключаються через repository-local exclude-файл Git;
- `.opencode/state/`, caches, logs, sessions, snapshots, runtime dependencies і bytecode локально виключаються;
- CodeSleuth не переписує мовчки відстежуваний `.gitignore` цільового репозиторію для цих patterns;
- `tools/codesleuth` навмисно не ігнорується, коли вибрано прив'язування залежності;
- звіти слід перевіряти/санітизувати перед навмисною публікацією;
- uninstall використовує conflict-safe restore і зберігає recovery evidence, коли змінений користувачем раніше наявний файл не можна відновити автоматично.

Точну семантику lifecycle див. у [`docs/PROJECT-LIFECYCLE.md`](docs/PROJECT-LIFECYCLE.md), а старий докладний експлуатаційний посібник, збережений для сумісності/довідки, — у [`docs/USER-GUIDE.md`](docs/USER-GUIDE.md).
