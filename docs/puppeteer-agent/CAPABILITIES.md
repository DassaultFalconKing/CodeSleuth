# Capabilities and boundaries

Puppeteer provides a high-level API for Chrome and Firefox over the Chrome
DevTools Protocol or WebDriver BiDi. For agents, its useful capabilities fall
into several groups.

## Page observation and interaction

- navigate pages and frames;
- inspect DOM, computed text, accessibility names, attributes, and page state;
- click, hover, scroll, type, select, upload files, and send keyboard/touch
  input;
- execute JavaScript in the page context;
- work with CSS, text, XPath, ARIA, and open Shadow DOM selectors.

Prefer `page.locator()` or `frame.locator()` for actions. Locators wait for the
element to exist and for action preconditions such as visibility, enabled state,
viewport presence, and a stable bounding box. Use lower-level element handles
only when the locator API cannot express the operation.

Accessibility selectors are usually more stable and user-meaningful than CSS
classes generated by a framework:

```js
await page.locator('::-p-aria([name="Save"][role="button"])').click();
await page.locator('::-p-text(Operation completed)').wait();
```

## Evidence and diagnostics

- full-page or element screenshots;
- PDFs using print CSS, or screen CSS after `page.emulateMediaType('screen')`;
- browser console, page errors, requests, responses, and failed-request logs;
- DevTools traces, optionally including screenshots;
- performance metrics and JavaScript/CSS coverage;
- DOM or structured JSON snapshots chosen by the test.

Screenshots prove rendered appearance at one viewport; they do not prove DOM
semantics, accessibility, network isolation, or absence of console errors.
Combine visual evidence with explicit assertions.

## Network control

Puppeteer can observe requests/responses and can intercept, continue, abort, or
fulfil requests. Once interception is enabled, every intercepted request must be
resolved or it remains stalled. Install the handler before navigation and make
all branches explicit:

```js
await page.setRequestInterception(true);
page.on('request', request => {
  const url = new URL(request.url());
  if (url.hostname === '127.0.0.1' || url.hostname === 'localhost') {
    void request.continue();
  } else {
    void request.abort('blockedbyclient');
  }
});
```

Request interception is test behavior, not a host security boundary. For
untrusted content or strict offline tests, also use runner/container network
controls and a minimally credentialed environment.

## Isolation and parallelism

Browser contexts isolate cookies and local storage and allow all pages for one
task to be closed together. Use a new context per scenario and a unique
`userDataDir` per browser process. Do not share the default user profile between
agents.

Parallel pages share one browser process and can still contend for CPU, memory,
download directories, service workers, and browser-global facilities. Start
with bounded concurrency and raise it only after measuring resource use.

## Launch versus connect

`puppeteer.launch()` creates a browser process owned by the task;
`browser.close()` should terminate it. `puppeteer.connect()` attaches to a
browser started elsewhere. For a connected browser, `browser.disconnect()`
detaches without shutting down that browser or its pages.

Agents should use `launch()` for disposable tests. Use `connect()` only when a
host explicitly provides a remote browser endpoint or the user asks to control
an existing session. Never guess or scan for debugging ports.

## Useful but non-authoritative outputs

Puppeteer can crawl SPAs, prerender content, test extensions, generate previews,
and gather performance traces. Those products remain derived evidence. They do
not replace application-level assertions, exact source identity, server logs,
or the repository's acceptance ledger.

## What Puppeteer does not guarantee

- that an arbitrary system Chrome is compatible with the installed Puppeteer;
- deterministic output without pinned browser/fonts/viewport/time/locale;
- safe execution when the Chrome sandbox is disabled;
- automatic cleanup after the controller is forcibly killed;
- correct test synchronization merely because a fixed sleep elapsed;
- that `networkidle` represents application readiness for long-polling or
  streaming applications;
- that a successful screenshot means interactive behavior works.
